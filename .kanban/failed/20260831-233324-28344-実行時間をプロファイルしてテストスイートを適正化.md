## Task

# 問題
MornKanbanのcard実行が毎回長く、実行画面では約173testが繰り返し走っているように見える。test数そのものが過剰なのか、subprocess/git worktree/temporary repository/PTY/server/LaunchAgent mock等の重いintegration test、workerとreviewerの重複実行、review retry/resolver等が支配的なのか不明。

# 目的
推測でtestを削らず、card 1件のend-to-end時間とtest suiteを計測してbottleneckを特定する。重複・過剰な待ち・非効率なfixtureだけを整理し、回帰検出力を落とさず通常iterationを短縮する。高速testと完全testの役割を明確にし、どの段階で何を走らせるかをMornKanban dispatcher/reviewer contractへ反映する。

# 計測
- 現在mainの全testを種類別に棚卸しする: pure unit、shell/CLI、git repository/worktree、Herdr mock、hook/config install、monitor HTTP、LaunchAgent、PTY、Node frontend state、contract/doc-lock、end-to-end。
- test file/test case単位のwall timeを複数回測定し、上位slow test、process起動回数、temporary git init/commit/worktree数、sleep/poll timeout、network access有無を一覧化する。
- 173件前後のtestに、同じ挙動を別card由来で重複検証しているもの、過去実装削除後も残るもの、同一fixtureを毎case作り直すものがないか調査する。
- 代表card History/dispatcher flowから、worker実装、worker test、reviewer起動、reviewerによる再test、review parse/retry、merge/resolver、Herdr pane setup/cleanupの各所要時間を計測する。test時間とagent思考/起動待ちを混同しない。
- review_enabled=true/falseの両flowで、reviewer省略がend-to-endへ与える差をmock計測する。
- 計測結果はworker回答/Card Historyに、変更前後の中央値、全test件数、wall time、slow上位、原因別比率として残す。恒久的な監査report fileを無闇にrepositoryへ追加しない。

# 適正化方針
- uniqueなregressionを単に件数削減のため消さない。過去に実際のbugを固定したtestは保持する。
- 完全に同一contractを同一levelで重複検証するtestだけ統合する。削除/統合時は何が別testで担保されるかを回答に対応表で示す。
- per-testのgit repo/process/server作成を安全に共有できる場合はclass/module fixtureへ集約する。ただしstate leak・順序依存・parallel不安定を作らない。
- 固定sleepをevent/condition/poll with short timeoutへ置換し、不要なtimeout満了待ちをなくす。
- 実CLI/実Herdr/実LaunchAgentを呼ぶtestはmock境界を見直し、最小限のintegration smokeだけ残す。mock argv/unitとE2Eの責務を分離する。
- subprocessを大量起動するdoc-lock/CLI表示testは、同じprocess結果を再利用できる範囲で集約する。
- Python/Node/shell標準機能だけを使い、外部test dependencyを追加しない。

# test tier
- 明確な2段階以上のrunner/commandを用意する:
  - fast: workerの通常iteration/reworkで数秒〜短時間に回す、unit・syntax・変更範囲の主要回帰。
  - full: merge前の最終gate、dispatcher/resolver/installer/monitor等を含む完全回帰。
- ただしfastだけでdoneにして重大回帰を逃さない。review_enabled=false時も、最終merge前に誰がどのfull gateを実行するかを明確にする。reviewerをOFFにしたprojectでreviewerをtest目的だけに起動しない。
- cardにtest commandが明記されている場合、project policy/tierとの優先順位を定義する。
- reviewerがworkerと全く同じfull suiteを無条件で二重実行しているなら、信頼境界を保ちながらartifact/result再利用または変更範囲別検証を検討する。worker自己申告だけを無検証で信用する設計にはしない。
- `KANBAN.md` frontmatterで `test_mode` / fast/full command等をproject別に設定できる設計が必要なら追加する。defaultは既存品質を落とさない値にする。

# 観測性
- dispatcher/card Historyへ、worker/reviewer/resolver/test/merge各phaseのdurationを機械可読かつ人間可読に記録する。秘密値やprompt全文は追加しない。
- monitorでcardのphase時間と総時間を確認できるようにし、「testが遅い」のか「agent/review待ち」なのか判別可能にする。
- timing instrumentation自体が目立つoverheadを増やさない。

# 完了条件
- 変更前baselineと変更後を同一machine・同一条件で最低3回測定し、中央値を比較する。
- 遅延原因をtest countではなく実測wall timeで説明する。改善が無い場合は無理なtest削除をせず、主因がagent/review等である証拠を報告する。
- fast tierとfull tierの収録test/保証範囲をcontract testで固定し、fullでは既存regressionがすべて実行されることを確認する。
- test統合後も、意図的に代表implementationを壊して対応testがfailするmutation spot-checkを行い、silent coverage lossがないことを確認する。
- test orderを変更/ランダム化してstate leakがないこと、process/tmp/worktree/port/lockをcleanupすることを確認する。
- 全shell `bash -n`、全Python `py_compile`、全JS syntax、最終full suite、skill validationを実行する。実HOME/remote/Herdr/LaunchAgentを変更しない。
- README/VERIFY/KANBAN.md templateへfast/full commandと利用段階、review OFFとの関係を簡潔に記載する。
- VERSIONはuser-facing CLI/policy変更がある場合のみ規約に従って更新する。日本語commit messageでcommitし、pushしない。
