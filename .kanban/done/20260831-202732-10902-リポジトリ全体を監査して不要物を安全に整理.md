## Task

# 目的
MornKanban repository全体を監査し、不要なdirectory/file、生成物、一時物、重複実装、古い配布資材、意図しない大容量file、不要なcommit/branch/worktree等が混入していないか確認する。機能・テスト・配布に必要な最小構成へ安全に整理し、`git clone`直後にも用途が分かるスッキリしたrepositoryにする。

# 重要な安全境界
- 調査と安全なcleanupは行うが、既存git historyのrewrite、rebase/squash、commit削除、force push、tag削除はしない。履歴整理が有益な場合は、対象commit・理由・影響・安全な実施案を報告するだけにする。
- pushしない。
- user dataを推測で削除しない。特に `.kanban/done`/`failed`のカード履歴、未解決card branch、stash、project registry、monitor config、LaunchAgent、他projectは保護する。
- untracked fileやdirty変更は他session/userの所有物として扱い、勝手に削除・上書き・stashしない。一覧と分類だけ行い、cleanup commitへ混ぜない。
- stale worktree/branch等を削除する場合は、merged済み・参照不要・成果がmainに存在することを機械的に確認できるものだけ。failed/unmerged branchは保持して報告する。

# 監査範囲
## repository tree
- `git ls-files`、`.gitignore`、top-level directory、各source/script/test/doc/static/configを棚卸しする。
- cache、log、coverage、bytecode、OS/editor file、build artifact、temporary answer、pid/lock、worktree生成物がtrackedまたはuntrackedで残る可能性を確認する。
- 同じ責務の旧GUI/CLI/monitor/setup実装、使われないscript/module/static asset、空directory placeholder、古いtemplate/skill copy、READMEから到達不能な資材を探す。
- fileごとにruntime・install/update配布・test・documentation・developmentのどこから参照されるかを `rg` 等で確認し、参照ゼロだけを理由に即削除せずentry pointやshell実行も確認する。
- 実行権限、shebang、line ending、macOS bash 3.2/Python標準library方針、skillのsource-of-truthとgenerated installed copyの境界を確認する。

## git metadata/history
- `git status --ignored`、branches、worktrees、stashes、tags、recent/full log、merge構造を調査する。
- 一時commit、同一変更の重複commit、誤って入った秘密情報らしき文字列、大容量binary、generated file、`.kanban-answer.md`等がhistoryにないか監査する。
- commit数を減らす目的だけのhistory rewriteはしない。不要に見えるcommitも既にmain historyなら保持し、将来の運用改善として報告する。
- merge済みkanban branchと未merge/failed branchを分類する。削除判断は上記安全境界に従う。

## 配布後の最小性
- fresh temporary clone相当で、VERSION、`kanban install/update/uninstall/version`、secretary skill配布、monitor、cross-project registry/send、Herdr scriptsがrepository内の必要資材だけで動くことを確認する。
- setup/installが不要fileをHOMEへ配布していないか、uninstallがinstaller-managed fileだけを消すか確認する。
- READMEのdirectory構成・command・保存場所が実treeと一致するようにする。不要な監査report fileをrepositoryへ恒久追加せず、結果はcard History/worker回答にまとめる。

# 実施方針
- 明確に不要で再生成可能、かつ参照・互換性・user dataへの影響がないtracked artifactは削除し、必要なignore ruleを追加する。
- 重複/旧実装を削除する場合は、現行entry pointと全テストが代替を保証することを示す。
- 空directoryがgitkeepで必要なruntime stateなら維持し、理由をREADMEまたは近接文書で簡潔に説明する。不要なplaceholderは削除する。
- cleanup前後のtop-level tree、tracked file数/size、削除対象と保持理由を回答に簡潔に示す。
- cleanupするものが無ければ、無理に変更commitを作らず、監査結果と「現状が最小」と判断した根拠を報告する。

# テストと完了条件
- repository内の全shellへ `bash -n`、全Python source/testへ `python3 -m py_compile` を実行する。
- 既存unittest/統合testをすべて実行する。monitor/LaunchAgent/test processは一時HOMEを使い必ずcleanupする。
- skill validator、CLI help/version、setupの非対話command、monitor serverの最小smoke、cross-project sendの一時project smokeを実行する。
- `git diff --check`、`git status --short --ignored`、tracked large-file確認、秘密情報のpattern auditを行う。検出値そのものを回答へ露出しない。
- cleanup後にmain由来のtemporary clone/worktreeでtestを再実行し、repository-localなuntracked fileに依存していないことを確認する。
- 変更がある場合のみVERSION規約を確認し、ユーザー向け配布挙動が変わる場合だけ適切にbumpする。単なるignore/doc/内部cleanupで不要なversion bumpをしない。
- 日本語commit messageでcommitし、pushしない。
