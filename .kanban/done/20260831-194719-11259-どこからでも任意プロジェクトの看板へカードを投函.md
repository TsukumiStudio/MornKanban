## Task

# 目的
MornKanbanを導入した各プロジェクトは、それぞれ独立した `.kanban/`、ポリシー、カード履歴、dispatcherを持つ。そのうえで、現在ディレクトリや会話セッションに依存せず、PC上のどこからでも登録済みの任意プロジェクトへカードを投入できるグローバルなCLI投函口を実装する。

想定例:
- Project A内または無関係なディレクトリからProject Bへ投入
- Project BからProject Aへ投入
- どのセッションからでも同じproject aliasを使って投入

# 必須仕様
## プロジェクト登録
- PC共通のproject registryを持ち、aliasとプロジェクトrootを登録・一覧・詳細表示・更新・削除できるCLIを提供する。例: `kanban projects add project-a /path/to/A`、`kanban projects list`、`kanban projects remove project-a`。
- aliasは安定して使え、重複・不正名・存在しないpath・`.kanban`を持たないpathを明確に拒否する。
- realpathで正規化・重複排除し、symlinkやpath traversalで登録外へ誤投函しない。
- 既にmonitor機能のproject discovery/config/registryが存在または統合中なら、設定を二重化せず共通化する。現在進行中/保持ブランチも含めリポジトリ状態を調査し、最終mainでmonitor一覧と投函先aliasが一致する設計にする。

## カード投函
- 例として `kanban send project-b "タイトル"` を提供し、本文はstdinまたは明示オプションから受け取れる。既存 `kanban add` と同等のbackend/model/threshold指定も必要に応じて転送する。
- コマンド実行元ではなく、必ず送信先Project Bの `.kanban/todo/` に通常のMornKanbanカードを作る。送信先の `.kanban/KANBAN.md` を既定backend/model/thresholdとして適用する。
- カードfrontmatterまたは追跡可能なメタデータに、投入元project alias（登録済みproject内からの場合）、投入元path、投函方式が分かる情報を記録する。秘密情報や環境変数値は記録しない。
- A→B、B→A、無関係ディレクトリ→Aのすべてを対称に扱う。
- 同時に複数セッションから同じprojectへ投函しても、ID衝突、部分書き込み、上書きが起きないatomicな作成にする。
- 投函はカード作成までを責務とする。monitor Webサイトは引き続き完全な読み取り専用で、書き込みAPIや操作ボタンを追加しない。
- 送信先dispatcherが動作中なら通常フローで拾えること。停止中の場合の表示/案内を明確にし、勝手にheadless workerへfallbackしない。visible Herdr contractを維持する。

## 互換性・配布
- bash 3.2互換、Pythonを使う場合は標準ライブラリのみ。
- 既存 `kanban add/init/run/monitor/install/update/uninstall/version` と秘書スキルを壊さない。
- CLI usage、README、セットアップ/アップデート配布、スキル原本を更新し、どのディレクトリから使うか、A→B/B→Aの例、registry保存先、dispatcher停止時の挙動を記載する。
- VERSIONを規約に沿って更新する。
